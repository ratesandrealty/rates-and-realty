## Resolved this session

### `tasks.origin` — the `related_table` conflation is gone

`related_table` used to answer two questions at once: *what is this task about*
and *who made it*. It now means only the first.

`tasks.origin` (`'system' | 'clickup' | 'user'`, NOT NULL) holds provenance.
Backfilled from the compound rule, **never from `related_table`** — which alone
would have marked 210 machine-created rows as human:

| | rows | origin |
|---|---|---|
| `related_table` set | 74 | `system` |
| `clickup_automation_log` entry | 210 | `clickup` |
| ClickUp id, no log entry | 30 | `clickup` — recorded judgement, all finished, none live |
| no id, no `related_table` | 11 | `user` |

**`clickup_enqueue` gates on `origin='system'`**, moved in the same migration as
the column. Before: `if v_t.related_table is null then return false;` — a proxy
that would have started pushing every human task the moment tagging gave one a
`related_table`. 251 tasks were one tag away.

New rows: `tg_tasks_set_origin` fills it — explicit wins, else `clickup_task_id`
present → `clickup`, else `auth.uid()` null → `system`, else `user`. The three SQL
creators (`surface_stale_leads`, `order_reminders_run`, `loan_order_set`) now also
state `origin='system'` explicitly, so a sweep triggered **by hand** produces
system tasks rather than user ones. `task_list` and `va_daily_tasks` read the
column instead of recomputing the compound rule, so two mechanisms cannot drift.

Full detail and proofs: `docs/HELD-task-tagging-and-bulk-2026-08-18.md`.

## Ready to build, with one decision outstanding

### Tagging — unblocked, but decide the slot first

Tagging a task to a referral partner or a third-party order is now **safe**: a
human tagging a task gets `origin='user'` whatever `related_table` says, so it is
not enqueued to ClickUp. Proven.

**The design call left: `related_table` is a single slot.** A task cannot be
tagged to both a referral partner and an order. Decide before building:

- reuse `related_table`/`related_id` (one tag per task, no schema change), or
- dedicated nullable columns (`referral_partner_id`, `loan_order_id`) allowing
  both, or
- a join table if tags should be many-to-many.

`referral_partners` has 9 rows; 34 tasks already point at a real `loan_orders`
row, so the link mechanism works either way.

### Bulk actions — design logged, not built

One RPC taking `uuid[]`: snapshot every matched row to `audit_log` **before**
deleting (`task_activity` cannot hold it — its FK is `ON DELETE CASCADE`), delete
in a **single statement**, and return the `clickup_task_id`s so the caller either
removes them all from ClickUp or reports exactly which survived. `task_upsert` and
`task_delete` take a single `p_id` today, so anything else is an N-call loop and
the bridge has no bulk route — a partial failure orphans an arbitrary number of
ClickUp tasks. One orphan is recoverable; twenty is not.

**~~The Maps suite flake.~~ FIXED 2026-08-19 — `ed5d5e8`.** Kept here because
the reasoning that left it unexplained is the reusable part.

The claim above — *"only two loaders exist repo-wide"* — **was wrong, and it is
why the mechanism went unexplained for so long.** That search covered `admin/`.
There is a **third** loader, `public/js/map-controls.js`, which owns
`window.loadGoogleMaps()`. Repo-wide, `admin/lead-detail.html` **and**
`public/unified-portal.html` load both it and `places-autocomplete.js`.

The two guards were **one-directional**:

| | appends a tag | looks for |
|---|---|---|
| `map-controls.js` | carrying `data-gmaps-js="1"` | **only** `script[data-gmaps-js="1"]` |
| `places-autocomplete.js` | **marked with nothing** | any `maps/api/js` tag |

So map-controls-first was adopted and stayed at one tag; places-first was
invisible to map-controls, which appended a second. Each module's own idempotence
guard (`_gmapsLoadPromise` vs `_loading`) is invisible to the other. The window is
real on every cold load: `loadGoogleMaps()` claims its promise and then **awaits
`fetch('/config')` before appending**, and a fresh context has no cached key. A
race decided by network latency is a flake, not a bug that reproduces on demand.

Fixed by marking the tag places-autocomplete creates — one attribute, guards
symmetric both ways.

**What actually broke the deadlock was refusing to fix it un-reproduced.** 31
consecutive clean runs had been captured while the suite kept failing; attribution
was established and mechanism was not. The new spec **`maps double-load forced
race`** pins the latency rather than waiting for it — delays `/config` 2500ms at
document-start and attaches a Places field at `DOMContentLoaded`, inside the gap.
**2 tags before the fix, 1 after**, both measured.

Two things it taught the harness, both kept:

- **`spec.atDocumentStart`** — a per-spec document-start script. Evals run after
  `readyState=complete`, and by then both loaders have latched module-private
  state that cannot be reset from outside. The first version of this probe drove
  the loaders from an eval and reported *"appended 0 tags"* for exactly that
  reason. **A defect that only exists during load cannot be reproduced after it.**
- **A probe that cannot set its race up returns a `HARNESS:` string, never a
  number.** Had it returned a healthy-looking `1` when the interleaving failed to
  form, that reads as the bug being fixed — the vacuous-pass failure this suite
  exists to catch.

Also caught while writing it: the spec's first `allowConsole` entry,
`'included multiple times'`, **never matched anything** — Google's wording is
*"...the Google Maps JavaScript API multiple times..."*. It was removed rather
than corrected, since a correct fix produces no warning to allow. A silencer that
matches nothing is the quietest blind spot there is.

**The better long-term shape, deliberately NOT built.** Both callers should go
through one loader — `loadGoogleMaps()`. It is not a like-for-like move:
`map-controls` requests **`&v=weekly`** and `places-autocomplete` does not, so
unifying them changes **which Maps version the page gets**, on pages that render
borrower addresses. That is a behaviour change needing its own verification, not
a tidy-up to fold into a flake fix. Until then the marker is what keeps the two
loaders honest, and **any third loader must set `data-gmaps-js="1"` on the tag it
appends and check for it before appending** — that is now the contract.

## Conventions worth keeping

- **Break-test before trusting.** Every spec added this session was run against
  the un-deployed page first and required to fail. Two of them passed
  *vacuously* on the first attempt (a panel that never mounted, and a stubbed
  query) and were rewritten — a green check on a surface that never rendered is
  the failure mode this suite exists to catch.
- **A stub proves rendering, never authorization or data.** The assignee picker
  shipped broken because its spec stubbed the query. Prove reads with a real
  session.
- **`clickup_outbox` and `clickup_task_cache` are service-role only.** An
  authenticated read returns 0 rows whatever is there; verify them with a
  privileged query or the result is meaningless.
- **Commit before deploy**, and restamp `?v=` pins whenever a pinned asset
  changes — `deploy.sh` refuses on stale pins, which is what it is for.
