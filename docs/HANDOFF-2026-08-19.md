## THE GREEN BAR IS TWO RUNS

```
node tools/render-check.mjs                              ->  75/75   477s
node tools/render-check.mjs --token tok.txt --token-only ->  8/8      45s
```

**There is no invocation that returns everything at once, by construction.** (The
second total grows as tokenOnly specs are added — 7 then 8 on 2026-08-19. Read it
off the run.) Do not look for
one. Running everything with `--token` returns **62/83, 21 failed, and not one is
a defect** — `--token` replaces the stub for *every* spec, so role-faked specs
(`spec.role:'va'` is the stub pretending; auth-guard recomputes the real role)
and stub-fabricated ones (e-sign wants a signer the fixture lacks; staff chat
wants a thread that does not exist) legitimately fail. A 21-failure token run
reads as twenty-one broken things and is not. Full reasoning in `CLAUDE.md`.

`ownerOnly` is a third state: needs **rene@'s own** session, excluded from both
modes, announced in both. Exactly one spec — the CRM board va-refusal — because
`requireAdmin()` checks a hardcoded one-address `ADMIN_EMAILS` allowlist and
redirects every account the harness can mint. Its server-side refusal is proven
by SQL independently; the spec is announced on every run so it cannot quietly
disappear.

## Shipped today

### Task system

**Bulk actions.** Checkboxes on task rows, a bar that appears only on selection,
and assign / complete / delete together.

- `task_delete_bulk(uuid[], p_force)` — snapshot every matched row to `audit_log`
  **first**, delete in a **single statement**, return every `clickup_task_id`
  from the snapshot. Reports `requested`, `matched` and `deleted` separately, so
  a partial cannot be read as a whole. All four branches proven: empty refused;
  all-missing refused with ids named; 2 real + 1 missing → 3/2/2 with both
  ClickUp ids; a sweeper task on an active lead refuses the **whole batch** with
  the safe row verified still present, and `p_force` then deletes both.
- `task_assign_bulk(uuid[], uuid)` — exists because `task_upsert` sets
  `due_date = p_due_date` with **no coalesce**, so the natural bulk assign would
  have silently wiped every due date. All-or-nothing on authorisation.
- Bulk complete is deliberately a **loop** over `task_set_status`: that function
  authorises per task, writes `task_activity` and drives `_task_clickup_sync`,
  and two mechanisms that must agree about "completed" is the drift this repo
  keeps paying for.

**"Someone else's" now names the person** — "Aubrey Ayson's tasks" — derived from
`task_assignees()`, not the rows on screen (which would flip the label as you
change folders). Reverts by itself when a third person can hold work.

**Tagging.** `referral_partner_id` and `loan_order_id` as nullable FKs with
`on delete set null`; pickers on the Add Task form; chips on the row. All 34
`related_table='loan_orders'` rows backfilled, 0 stranded.
`order_reminders_run` writes the new column **alongside** the old pair and its
duplicate check reads **both**, so no reader sees neither mid-changeover.
Detail: `docs/TASK-TAGGING-BUILT-2026-08-19.md`.

### Task row — discoverability, and the signals it was discarding

Detail: `docs/TASK-ROW-SIGNALS-2026-08-19.md`.

- **Bulk select is now visibly possible.** The bar was already fully wired; what
  was missing was any affordance saying selection existed before you ticked
  something. A header row (select-all + "Select for bulk actions" + `N shown`),
  a select-all that works **both ways** with an indeterminate state, and the bar
  made `position: sticky` so a long list cannot put the count and Delete above
  the fold.
- **Four due states, not two.** `bucket` always returned
  `overdue|today|upcoming|no_date`; only overdue was drawn, and the line was
  omitted entirely with no date — so **29 of 42 live tasks** looked identical to
  one due next week. `no_date` is now visible and deliberately the **quietest**
  of the four: it is an unmade decision, not a fault, and 29 amber rows would
  teach people to ignore the colour that matters. Bucket comes from the server so
  it cannot drift from the VA board's rule.
- **Provenance from `origin`,** never a heuristic — 320 of 331 tasks are
  machine-made and looked exactly like something typed by hand. Only the machine
  case is marked (`⚙ auto`); human is the unmarked default at 11 rows.
  `question_pending` deliberately skipped: wired, but 0 rows, and styling an
  invisible state proves nothing.
- **Order cards show `N open task(s)`** and click through to the Tasks tab. Open
  only, silent at zero, one query per pane rather than per card. 38 tasks carry
  `loan_order_id` and every one was raised by `order_reminders_run` — its output
  was previously invisible next to the thing it is about.
- **Partner section HELD** (0 tasks partner-tagged, it would be an empty
  surface), but **both `referral_partner_id` columns now carry a `COMMENT`**.
  `contacts.referral_partner_id` is lead attribution read by the whole partner
  reporting family; `tasks.referral_partner_id` is a per-task subject tag **none
  of them read**. Renaming was rejected — the name is right for what it holds,
  and the hazard is the assumption that partner reporting includes tasks, which a
  comment dispels and a rename would only relocate.

## What remains

### `clickup-bridge` — the last open Tier A function

`docs/HELD-clickup-bridge-guard-2026-08-19.md`. **Not a `requireStaff` drop-in.**
pg_cron job 15 and `sms-assistant` reach it with **no Authorization header by
design**, and deploying it unpinned once 401'd every caller for days with nothing
alerting — the fourth instance of that exact failure.

Order, and it must not be compressed:

1. Re-header pg_cron job 15 to `internal_call_headers()` **first**, and confirm a
   production run by reading `net._http_response` — not `cron.job_run_details`,
   which only ever means the request was queued.
2. Give `sms-assistant` the service key on its two bridge calls.
3. **Then** `requireStaff(req, { allowInternal: true })`, before `req.json()`.
4. `verify_jwt` stays **false**. The pin is correct; the in-function guard is the
   control.

Five of its six browser callers still send the anon key and move to `fnFetch`
first, exactly as `bot-admin` and `lead-scorer` did.

## Two measurement lessons, because both changed a fix

### A 0×0 reading was a closed tab, not a CSS bug

Measuring the bulk bar reported **every element as 0×0** — checkbox, bar, the
lot. That reads as a styling defect and the obvious response is to restyle it.

It was wrong. The Tasks tab was `display:none`, and every descendant of a hidden
panel measures 0×0. With the tab opened first: checkbox 14×14, bar 1109×50, all
six controls present and working.

**Trusting it would have restyled a correctly-styled checkbox and left the real
gap untouched** — that nothing on screen announced selection was possible. The
component was fine; the affordance was missing. Same family as the stub trap
already in `CLAUDE.md`, seen from the measurement side: **a working thing can be
made to look broken by the conditions you measure it under.** Open the panel,
scroll it into view, then measure.

### The green bar drifted 7 → 8 within a day

`--token-only` returned 7/7 in the morning and 8/8 in the afternoon, because a
tokenOnly spec was added in between — which made the number written into
`CLAUDE.md` and into this file stale on the day it was written.

**The durable claim is "two runs, and neither total covers everything".** The
second number is **read off the run**, never off a document. A count that drifts
is worse than no count: it is exactly what somebody checks against, and when it
disagrees they stop trusting the whole note.

## Conventions that earned their keep today

- **Prove both directions.** The toast, the reminder, the follow-up button and
  the folder label each had a branch that a one-sided test would have passed
  while wrong. Two of them *were* wrong and only the second direction showed it.
- **A self-cleaning spec beats a fixture.** The bulk-select, tagging and
  follow-up specs each create what they need and delete it, so no row exists that
  someone must remember not to delete.
- **Comments belong INSIDE the function body.** `recapture-db-functions` reads
  `pg_get_functiondef`, which returns the `CREATE` and nothing above it. Verified
  today: the in-body rationale survived a recapture; anything above would have
  vanished.
- **Changing a `RETURNS TABLE` drops the grants.** The drop is mandatory, and the
  grants go with it — the function stays present while every browser call fails
  `permission denied`. Capture and restore them explicitly.
