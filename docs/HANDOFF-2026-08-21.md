### The eight divergence winners — decided, in `docs/TOOLBAR-CONSOLIDATION-DIVERGENCE-2026-08-20.md`

1. **link URL validation** → validate (`https?:`/`mailto:`/`tel:`). Main and drip
   currently have no scheme check at all.
2. **link prompt default** → prefill `https://`
3. **`execCommand` error handling** → `try/catch`. An uncaught throw abandons the
   rest of the click handler.
4. **focus handling** → the main composer's focus-before-and-after. The one place
   it is the better implementation; without it a toolbar click can collapse the
   selection and apply the command to nothing.
5. **font list** → named faces with a fallback stack (`Arial, Helvetica, sans-serif`)
6. **size scale** → named sizes on the legacy scale (Small 2 / Normal 3 / Large 5 /
   Huge 6). Also fixes a live bug: main's options are **out of order** — value 4
   "14" is listed above value 3 "12".
7. **controls present** → union for the **formatting core**; insert controls
   (Canva, Loom, emoji, image, variable picker) become **host-passed slots**, not
   toolbar defaults. A signature has no variables; a drip step has no Loom.
8. **dispatcher shape** → `(cmd, value)` with an explicit target element. Drip's
   `fmtText(cmd)` takes **no value argument** and structurally cannot support
   font, size, colour or highlight — it has to go regardless of preference.

### The colour decision — settled by the client test

All three clients rendered correctly, **Outlook included**: lines 1 and 2 red,
line 3 yellow on inline style, line 4 yellow on the fallback.

- **Highlight ships as an inline `style` on a span.** The `<td bgcolor>` fallback
  is **not needed**, so no custom selection-wrapping command is required —
  `hiliteColor`/`backColor` through `execCommand` is sufficient.
- **Text colour ships as inline style too**, so there is one representation rather
  than two.
- **`styleWithCSS` on for the COLOUR COMMANDS ONLY.** Globally would change what
  bold and underline emit (`<span style="font-weight:700">` instead of `<b>`)
  across every email this CRM sends, and `<b>`/`<u>` are better supported in mail.

## Shipped this session

### The inline conversation now uses the card's width

Measured trace at a 1039px viewport, outer to inner:

```
ld-body 1034 → ld-main      764   -270   the 260px left nav (--sidebar-w)
ld-tab-panel → DIV          708    -56   .ld-tab-panel { padding:28px 28px 60px }
DIV          → lp-card      664    -44   wrapper padding
lp-card      → lpOrdersBody 627    -37   .lp-card { padding:16px 18px } + border
lpOrdersBody → lpHoiQuotes  619     -8   the order row's padding:6px 8px
lpHoiQuotes  → lpHoiBody    600    -19   the quote card's padding
```

164px across five levels. **Fixed:** the thread host is outdented by the last two
drops (8 + 19 = 27) and spans the orders-body width, **600 → 627**. Those two space
the quote card's *content*, and a conversation is that card's full-width detail
view, not content within it.

**Why the 270px nav and the 56px tab padding were left alone:**

- The **nav is structural**. 260px is a fixed cost, so its *share* shrinks as the
  window grows — 26% at 1039px, ~10% at 2560. Reclaiming it means changing the
  page's layout for every tab, not fixing a column.
- The **56px tab padding** is what separates every card on the page from the
  viewport edge. Removing it for one panel would make the conversation the only
  element touching the frame.
- Not outdented past the `.lp-card` padding either (another 37px) — that puts the
  thread flush against the card border, which reads as broken rather than wide.

Guarded to `min-width: 900px`: `.ld-main` is `overflow-x:hidden`, so a negative
margin on a narrow viewport would **clip rather than scroll**.

`gm-msg` measuring 0 is expected — collapsed messages are `display:none`.

`gmail_message_id` per event; `inbox.js` tags messages `data-mid` and accepts
